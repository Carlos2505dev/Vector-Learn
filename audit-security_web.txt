=========================================
CAMADA W1 — OWASP TOP 10 2021 (A01–A10)
=========================================

-----------------------------------------
A01:2021 — BROKEN ACCESS CONTROL
-----------------------------------------
REGRA: O servidor NUNCA deve confiar na decisão de acesso do cliente.
Todo controle de autorização DEVE ser verificado no backend.

TESTE:
- Acessar endpoints protegidos sem token → deve retornar 401/403
- Acessar endpoint de admin sem role de admin → deve retornar 403
- Modificar ID de recurso na URL/body para acessar dados de outro usuário (IDOR)
- Testar método HTTP não autorizado (POST em rota GET-only, DELETE em rota read-only)
- Verificar se o JWT contém role/permissions e se o servidor valida
- Testar forçando browser a fazer cross-origin request com credenciais
- Verificar se existe rate limiting por role (admin não deve ter mais requests que user)
- Testar acesso a endpoints de diagnóstico/debug em produção (/debug, /admin, /metrics)
- Verificar se diretórios sem index.html retornam listing de arquivos (directory traversal)
- Testar bypass de path: /../, /..;/, /..%2f, /%2e%2e%2f

IMPACTO DE FALHA: Privilege escalation, IDOR, data exfiltration, admin takeover.

-----------------------------------------
A02:2021 — CRYPTOGRAPHIC FAILURES
-----------------------------------------
REGRA: Nunca implementar criptografia customizada. Usar bibliotecas padrão.

TESTE:
- Verificar se dados sensíveis são transmitidos em TLS 1.2+ (não SSLv3, TLS 1.0, TLS 1.1)
- Verificar cipher suites: desabilitar RC4, DES, 3DES, MD5-based MACs
- Verificar se senhas usam bcrypt/argon2 (não MD5, SHA-1, SHA-256 sem salt)
- Verificar se há hash de senha no banco: deve ser bcrypt com salt ≥ 12 rounds
- Verificar se tokens de API são de alta entropia (≥ 128 bits)
- Verificar se o site redireciona HTTP → HTTPS (301/302, não apenas HSTS)
- Verificar se cookies de sessão usam Secure flag (não enviados em HTTP)
- Verificar se há dados sensíveis em cache do navegador (Cache-Control: no-store)
- Verificar se há dados sensíveis em logs de servidor (senhas, tokens, PII)
- Verificar se a chave de assinatura JWT é ≥ 256 bits e não está hardcoded

IMPACTO DE FALHA: Data breach, credential theft, MITM, password cracking.

-----------------------------------------
A03:2021 — INJECTION
-----------------------------------------
REGRA: TODA entrada do usuário tratada como DATA, nunca como código.

TESTE — SQL Injection:
- Inserir ' OR 1=1-- em campos de login, busca, filtros
- Testar UNION-based: ' UNION SELECT NULL,NULL,NULL--
- Testar Time-based blind: ' OR SLEEP(5)--
- Testar Boolean-based: ' AND 1=1-- vs ' AND 1=2--
- Testar em parâmetros de URL: ?id=1' OR '1'='1
- Testar em headers customizados
- Verificar se erros de SQL aparecem na resposta (stack trace com query)
- Verificar se ORM/prepared statements são usados corretamente

TESTE — XSS:
- Reflected XSS: injetar <script>alert(1)</script> em parâmetros de URL
- Stored XSS: injetar em campos de formulário, perfil, comentários
- DOM XSS: manipular #fragment, postMessage, document.referrer
- XSS via SVG upload: <svg onload=alert(1)>
- XSS via attribute injection: " onfocus="alert(1)" autofocus="
- XSS via event handlers: <img src=x onerror=alert(1)>
- Testar com CSP habilitado: deve bloquear inline scripts
- Verificar se innerHTML, dangerouslySetInnerHTML, v-html sanitizam input

TESTE — Command Injection:
- Injetar ; ls, | cat /etc/passwd, $(whoami) em campos de input
- Testar em endpoints que processam filenames, URLs, ou parâmetros de shell
- Verificar se child_process, exec, spawn não recebem input direto do usuário

TESTE — LDAP/NoSQL/Template Injection:
- Injetar *)(uid=*))(|(uid=* em campos de autenticação LDAP
- Injetar {"$gt": "", "$ne": ""} em APIs MongoDB
- Testar SSTI: {{7*7}}, ${7*7} em campos renderizados por template engine
- Verificar se a resposta é 49 (SSTI confirmado)

TESTE — Header Injection / CRLF:
- Injetar %0D%0A em headers: X-Forwarded-For, User-Agent
- Verificar se o servidor rejeita ou sanitiza CRLF em headers de resposta

IMPACTO DE FALHA: Full DB dump, RCE, cookie theft, session hijacking, data exfiltration.

=========================================
CAMADA W2 — SEGURANÇA DE SESSÃO WEB
=========================================
REGRA: Sessões web são o alvo #1 de ataques. Proteger com todas as camadas.

Cookie Flags (obrigatório):
  Set-Cookie: session=...;
    HttpOnly          → JavaScript não acessa o cookie (mitiga XSS)
    Secure            → Cookie só é enviado em HTTPS
    SameSite=Lax      → Proteção contra CSRF (ou Strict para apps sensíveis)
    Path=/            → Limitar escopo do cookie
    Max-Age=3600      → Expiração máxima de 1 hora para sessões
    Domain=.example.com → Não definir subdomínios mais amplos que necessário

TESTE:
- Verificar se cookies de sessão têm HttpOnly (usar document.cookie → deve retornar vazio)
- Verificar se cookies têm Secure (inspecionar em conexão HTTP → cookie não deve ser enviado)
- Verificar se SameSite é Lax ou Strict (testar cross-origin POST → deve bloquear)
- Verificar se há cookie de sessão APÓS login (deve existir HttpOnly session cookie)
- Verificar se há timeout de sessão inativo (≤ 15 min)
- Verificar se sessão é invalidada após logout (cookie deve ser deletado)
- Verificar se há token CSRF em formulários (hidden field ou header customizado)
- Verificar se o servidor valida o token CSRF em cada mutation request
- Verificar se session fixation é prevenida (token deve mudar após login)
- Verificar se múltiplas sessões simultâneas são permitidas/controladas
- Verificar se há mecanismo de "logout all devices" (revogação em massa)

Armazenamento de tokens no browser:
  - NUNCA: localStorage para tokens (acessível via XSS)
  - NUNCA: sessionStorage para tokens críticos (acessível via XSS)
  - OBRIGATÓRIO: HttpOnly cookies para access tokens
  - Alternativa: memory + refresh token via HttpOnly cookie (SPA moderna)
  - Para SPAs: usar BFF (Backend-for-Frontend) pattern

IMPACTO DE FALHA: Session hijacking, CSRF, token theft, privilege escalation.

=========================================
CAMADA W3 — PROTEÇÃO CSRF (CROSS-SITE REQUEST FORGERY)
=========================================
REGRA: Toda mutation (POST, PUT, PATCH, DELETE) DEVE ter proteção CSRF.

Estratégias obrigatórias (usar pelo menos uma):
  1. SameSite=Strict/Lax no cookie de sessão
  2. Token CSRF synchronizer pattern (token no hidden field + validação server-side)
  3. Custom header check (X-Requested-With, X-CSRF-Token)
  4. Double Submit Cookie Pattern

TESTE:
- Criar formulário HTML externo que faz POST para endpoint autenticado
  <form action="https://app.example.com/api/transfer" method="POST">
    <input type="hidden" name="amount" value="10000">
    <input type="hidden" name="to" value="attacker-account">
  </form>
  <script>document.forms[0].submit()</script>
- Verificar se o POST é BLOQUEADO (403 Forbidden, não 200 OK)
- Verificar se SameSite=Strict/Lax está configurado no cookie
- Verificar se há token CSRF no formulário
- Verificar se mutations via AJAX exigem header customizado
- Verificar se GET requests não causam efeitos colaterais (state-changing via GET = vulnerabilidade)
- Testar com subdomínio: attacker.subdomain.example.com → CSRF deve ser bloqueado se SameSite=Lax
- Testar cross-origin: evil.com → deve bloquear se SameSite=Strict/Lax

IMPACTO DE FALHA: Ação não autorizada em nome do usuário (transferência, alteração de dados).

=========================================
CAMADA W4 — CSP (CONTENT SECURITY POLICY) AVANÇADO
=========================================
CSP é a linha de defesa contra XSS. Deve ser configurado como DENY-first.

CONFIGURAÇÃO MÍNIMA RECOMENDADA:
  Content-Security-Policy:
    default-src 'none';
    script-src 'self' 'nonce-{random}';
    style-src 'self' 'unsafe-inline';
    img-src 'self' data: https://cdn.example.com;
    font-src 'self';
    connect-src 'self' https://api.example.com;
    frame-ancestors 'none';
    base-uri 'self';
    form-action 'self';
    object-src 'none';
    upgrade-insecure-requests;

TESTE:
- Verificar se CSP está presente: curl -I https://app.example.com
- Verificar se usa report-uri ou report-to (CSP violation reporting)
- Verificar se 'unsafe-inline' está ausente em script-src (ou usa nonce/hash)
- Verificar se 'unsafe-eval' está ausente em todo o CSP
- Verificar se frame-ancestors está configurado (previne clickjacking)
- Verificar se base-uri está configurado (previne base tag injection)
- Verificar se form-action está configurado (previne form hijacking)
- Testar XSS com CSP habilitado: deve ser bloqueado
- Verificar se CSP não está em meta tag (deve ser header HTTP)
- Verificar se CSP usa Report-Only em produção antes de enforcement

IMPACTO DE FALHA: XSS persistente, data theft, credential harvesting.

=========================================
CAMADA W11 — VULNERABILIDADES AVANÇADAS WEB
=========================================

-----------------------------------------
Race Conditions / TOCTOU (Time-of-Check to Time-of-Use):
-----------------------------------------
REGRA: Operações de negócio que dependem de estado devem ser atômicas no servidor.
Múltiplos requests paralelos não devem conseguir manipular o mesmo recurso.

TESTE:
- Enviar 10 requests simultâneos para aplicar o mesmo cupom → deve aplicar apenas 1
- Enviar 2 transferências simultâneas com o mesmo saldo → apenas 1 deve ser processada
- Testar com ferramenta de concorrência: wrk, Apache Bench com múltiplos workers
- Verificar se o servidor usa transações de banco (SELECT ... FOR UPDATE)
- Testar race condition em: cupons, promoções, estoque, transferências, leilões
- Verificar se idempotency keys são usadas para mutations

IMPACTO DE FALHA: Double-spend, cupom fraudulento, overselling de estoque.

-----------------------------------------
JWT Algorithm Confusion:
-----------------------------------------
REGRA: O servidor DEVE validar o algoritmo do JWT e rejeitar algoritmos não autorizados.

TESTE:
- Modificar header JWT: {"alg": "none"} → deve retornar 401 (não 200)
- Modificar header JWT: {"alg": "HS256"} com chave pública como secret → deve retornar 401
- Testar se o servidor aceita apenas o algoritmo esperado (RS256, ES256, etc.)
- Verificar se a chave de verificação é do tipo correto (pública vs simétrica)
- Testar key confusion: assinar com chave pública usando HS256
- Verificar se "none" algorithm é rejeitado em TODOS os endpoints

IMPACTO DE FALHA: Signature bypass, account takeover, privilege escalation.

-----------------------------------------
OAuth 2.0 / OIDC Vulnerabilities:
-----------------------------------------
TESTE:
- redirect_uri: testar com URI de atacante → deve ser rejeitado (whitelist obrigatório)
- state parameter: verificar se é obrigatório e validado (previne CSRF no fluxo OAuth)
- PKCE (Proof Key for Code Exchange): verificar se é obrigatório para public clients
- Verificar se tokens de acesso são de curta duração (≤ 15 min)
- Verificar se refresh tokens são rotacionados a cada uso
- Testar token leakage via: Referer header, URL fragment, logs de servidor
- Verificar se scopes são minimalistas (principle of least privilege)
- Testar open redirect via parâmetro de callback do OAuth
- Verificar se id_token é validado (issuer, audience, nonce, exp)

IMPACTO DE FALHA: Account takeover via OAuth, token theft, session fixation.

-----------------------------------------
Prototype Pollution:
-----------------------------------------
REGRA: NUNCA permitir que input do usuário modifique __proto__, constructor, ou prototype.

TESTE:
- Injetar {"__proto__": {"isAdmin": true}} em JSON body
- Injetar {"constructor": {"prototype": {"role": "admin"}}}
- Verificar se merge/extend de objetos filtra chaves perigosas
- Testar em: JSON.parse(), Object.assign(), spread operator com input malicioso
- Verificar se libraries de merge (lodash.merge, deepmerge) são seguras
- Testar via query params: ?__proto__[admin]=true

IMPACTO DE FALHA: RCE (via __proto__.output), privilege escalation, property injection.

-----------------------------------------
HTTP Request Smuggling:
-----------------------------------------
REGRA: O servidor e o proxy devem concordar sobre os limites dos HTTP requests.

TESTE:
- CL.TE: enviar request com Content-Length e Transfer-Encoding conflitantes
  POST / HTTP/1.1\r\nHost: app.example.com\r\nContent-Length: 6\r\nTransfer-Encoding: chunked\r\n\r\n0\r\n\r\nX
- TE.CL: transferência chunked com Content-Length menor
- Verificar se o servidor rejeita requests com ambos os headers
- Testar se HTTP/2 → HTTP/1.1 downgrading é seguro
- Verificar se proxies/load balancers normalizam requests corretamente

IMPACTO DE FALHA: Cache poisoning, request hijacking, WAF bypass.

-----------------------------------------
Subdomain Takeover:
-----------------------------------------
TESTE:
- Enumerar subdomínios: subfinder, amass, assetfinder
- Verificar CNAME records: subdomínios apontando para serviços non-existent
  (ex: app.herokuapp.com sem app deployado, app.azurewebsites.net vago)
- Verificar se serviços third-party (Heroku, Netlify, Vercel, GitHub Pages) são reivindicados
- Verificar se wildcard DNS (*.example.com) está configurado perigosamente
- Testar takeover: criar conta no serviço apontado e servir conteúdo malicioso

IMPACTO DE FALHA: Phishing via subdomain legítimo, session theft, content injection.

-----------------------------------------
DNS Rebinding:
-----------------------------------------
REGRA: O servidor deve validar o Host header e não resolver nomes internos.

TESTE:
- Configurar domínio que resolve primeiro para IP público, depois para 127.0.0.1
- Testar se o servidor acessa services internos via DNS rebinding
- Verificar se o servidor valida Host header contra whitelist
- Testar com IP literal: http://127.0.0.1:PORT/
- Verificar se requests internos são bloqueados (SSRF via DNS rebinding)

IMPACTO DE FALHA: Internal network scanning, service discovery, cloud metadata theft.

-----------------------------------------
postMessage Security:
-----------------------------------------
REGRA: TODOS os event listeners de message DEVE validar o origin do remetente.

TESTE:
- Verificar se addEventListener("message") valida event.origin
- Testar envio de postMessage com origin malicioso
- Verificar se dados recebidos via postMessage são validados ANTES de processamento
- Testar se window.opener.postMessage pode ser abusado (reverse tabnapping)
- Verificar se *.example.com não é aceito como origin válido

IMPACTO DE FALHA: XSS via postMessage, data injection, session hijacking.

-----------------------------------------
Business Logic Abuse:
-----------------------------------------
TESTE:
- Aplicar cupom com valor negativo → deve ser rejeitado
- Modificar preço no body do request: {"price": -100} → deve usar preço do servidor
- Comprar item com estoque zero → deve retornar erro
- Aplicar múltiplos cupons que não deveriam ser combináveis
- Usar desconto de 100% em item premium → deve ter limite
- Enviar quantity negativa no carrinho → deve ser rejeitado
- Alterar role de "user" para "admin" no body do request
- Modificar expiração de cupom ou assinatura
- Reenviar request de pagamento processado (replay attack)

IMPACTO DE FALHA: Fraude financeira, manipulação de preços, acesso não autorizado.

-----------------------------------------
Secure Randomness:
-----------------------------------------
REGRA: NUNCA usar Math.random() para dados sensíveis. Usar CSPRNG.

TESTE:
- Verificar se tokens usam crypto.getRandomValues() ou equivalente (não Math.random())
- Verificar se nonces CSRF são gerados com CSPRNG
- Verificar se state parameter do OAuth é de alta entropia (≥ 128 bits)
- Verificar se session IDs são gerados com entropia suficiente (≥ 128 bits)
- Verificar se PINs, códigos de verificação usam RNG seguro

IMPACTO DE FALHA: Token prediction, session fixation, CSRF bypass.

-----------------------------------------
HTTP/2 Specific Attacks:
-----------------------------------------
TESTE:
- Rapid Reset (CVE-2023-44487): enviar streams com RST_STREAM imediato
  → verificar se servidor limita concorrência de streams
- Verificar se MAX_CONCURRENT_STREAMS está configurado (≤ 100)
- Verificar se frame size está limitado (≤ 16KB padrão)
- Testar com ferramenta: h2load, hyper
- Verificar se server push está desabilitado (pode ser abusado)

IMPACTO DE FALHA: DoS via rapid reset, resource exhaustion, service disruption.

-----------------------------------------
Web Cache Poisoning:
-----------------------------------------
TESTE:
- Manipular X-Forwarded-Host: injectar JavaScript que é servido via cache
- Manipular X-Forwarded-Scheme: forçar HTTP em vez de HTTPS
- Testar cache key injection: adicionar header não-cacheável ao key
- Verificar se respostas cacheadas validam todos os headers de input
- Testar com Fat GET: enviar GET com body (pode confundir caches)

IMPACTO DE FALHA: XSS persistente via cache, defacement, credential theft.

-----------------------------------------
ReDoS (Regular Expression Denial of Service):
-----------------------------------------
REGRA: Evitar regexes com backtracking exponencial em input do usuário.

TESTE:
- Identificar regexes no código: /regex/g no source
- Testar com inputs que causam backtracking: aaaaaaaaaaaaaaaaaaaaaaaac
- Ferramentas: safe-regex, regex101.com (análise de complexidade)
- Verificar se validação de email/URL usa regex seguras
- Testar com payload longo: 10.000+ caracteres em campos validados por regex

IMPACTO DE FALHA: CPU exhaustion, DoS, service degradation.

-----------------------------------------
JSONP Risks:
-----------------------------------------
REGRA: NUNCA usar JSONP em produção. Usar CORS + fetch/XHR.

TESTE:
- Verificar se endpoints retornam response com callback parameter
- Testar se callback parameter aceita qualquer valor (XSS via callback name)
- Verificar se Content-Type é application/json (não application/javascript)
- Verificar se JSONP endpoints validam Origin

IMPACTO DE FALHA: XSS via JSONP callback, data theft cross-origin.

-----------------------------------------
CORS Preflight Bypass:
-----------------------------------------
TESTE:
- Enviar request com method não-padrão (PATCH, DELETE) que não dispara OPTIONS
- Verificar se o servidor aceita methods não listados em Access-Control-Allow-Methods
- Testar se headers customizados bypassam preflight
- Verificar se Access-Control-Allow-Origin: * não está em endpoints autenticados
- Testar com Origin: null (pode bypassar em alguns browsers)

IMPACTO DE FALHA: CSRF via bypass de preflight, cross-origin data theft.

-----------------------------------------
Account Enumeration via Timing:
-----------------------------------------
TESTE:
- Medir tempo de resposta para email existente vs inexistente
- Usar ferramenta: turbo Intruder, custom script com medição precisa
- Diferença > 50ms pode indicar account enumeration
- Verificar se todas as rotas de autenticação retornam tempo uniforme
- Testar: cadastro, login, reset de senha, verificação de email

IMPACTO DE FALHA: Account enumeration, targeted attacks, privacy violation.

-----------------------------------------
Integer Overflow:
-----------------------------------------
TESTE:
- Enviar valores numéricos extremos: 99999999999999999999
- Enviar valores negativos em campos que esperam positivos
- Testar overflow em: quantidade, preço, desconto, paginação, offsets
- Verificar se backend valida ranges de números (MIN/MAX)
- Testar com MAX_INT + 1, MIN_INT - 1

IMPACTO DE FALHA: Unexpected behavior, data corruption, logic bypass.

-----------------------------------------
Open Redirect:
-----------------------------------------
TESTE:
- Verificar parâmetros de redirect: ?redirect=/dashboard, ?next=/admin
- Testar com URL externa: ?redirect=https://evil.com
- Verificar se servidor valida redirect contra whitelist de domínios
- Testar bypass: ?redirect=//evil.com, ?redirect=/\evil.com, ?redirect=https://app.example.com@evil.com
- Verificar se redirects usam paths relativos apenas (/path, não //host)

IMPACTO DE FALHA: Phishing via redirect autêntico, credential theft, OAuth token theft.

-----------------------------------------
HTTP/3 / QUIC Security (se aplicável):
-----------------------------------------
TESTE:
- Verificar se QUIC implementa encryption-by-default (obrigatório no RFC 9001)
- Verificar se handshake não permite downgrade para HTTP/2 inseguro
- Verificar se connection migration não bypassa controles baseados em IP
- Verificar se 0-RTT não permite replay de requests sensíveis

IMPACTO DE FALHA: Replay attack, downgrade attack, IP-based control bypass.

=========================================
CHECKLIST FINAL PRÉ-PENTEST — WEB (OWASP TOP 10 + ASVS)
=========================================
--- Broken Access Control (A01) ---
[ ] Controles de acesso validados no servidor (nunca apenas no cliente)
[ ] IDOR testado: recursos de outros usuários inacessíveis
[ ] Métodos HTTP restritos por endpoint
[ ] Endpoints de debug/admin não expostos em produção
[ ] Directory listing desabilitado

--- Cryptographic Failures (A02) ---
[ ] TLS 1.2+ obrigatório, cipher suites seguros
[ ] Senhas com bcrypt/argon2 (≥ 12 rounds), nunca MD5/SHA-256
[ ] Dados sensíveis não em cache do navegador (Cache-Control: no-store)
[ ] Chave JWT ≥ 256 bits, não hardcoded
[ ] HTTP → HTTPS redirect (301) configurado

--- Injection (A03) ---
[ ] SQL Injection testado em todos os inputs (parâmetros, headers, URL)
[ ] Reflected XSS testado em todos os parâmetros de URL
[ ] Stored XSS testado em campos de perfil, comentários, uploads
[ ] DOM XSS testado via postMessage, fragment, referrer
[ ] Command Injection testado em campos que interagem com sistema
[ ] SSTI testado: {{7*7}} deve retornar 49 se vulnerável
[ ] CRLF injection testado em headers

--- Insecure Design (A04) ---
[ ] Threat model documentado
[ ] Fluxos de negócio críticos têm controles anti-abuso
[ ] Trust boundaries definidas e testadas

--- Security Misconfiguration (A05) ---
[ ] Páginas default removidas (Apache/Nginx status pages)
[ ] .git/.env/.DS_Store não acessíveis via HTTP
[ ] CORS sem wildcard em endpoints autenticados
[ ] Debug mode desabilitado em produção
[ ] Erros não expõem stack traces ao cliente

--- Vulnerable Components (A06) ---
[ ] npm audit / yarn audit: 0 Critical/High pendentes
[ ] Framework em versão suportada (não EOL)
[ ] Lockfile commitado (package-lock.json / yarn.lock)
[ ] Dependências com CVEs remediadas

--- Auth Failures (A07) ---
[ ] Rate limiting em login (≥ 5 tentativas → lockout 15 min)
[ ] 2FA/MFA disponível e obrigatório para contas admin
[ ] Tokens de reset de senha: uso único, expiração ≤ 1 hora
[ ] Sessão invalidada após change password
[ ] Mensagem genérica em "esqueci a senha"
[ ] Cookies: HttpOnly + Secure + SameSite=Lax/Strict

--- Data Integrity Failures (A08) ---
[ ] SRI (Subresource Integrity) em <script> e <link> de terceiros
[ ] CI/CD pipeline protegido contra modificações
[ ] Hot updates assinados e verificados

--- Logging Failures (A09) ---
[ ] Logs de login falhos com IP, timestamp, user_agent
[ ] Logs sem PII, tokens, senhas
[ ] Alerta para 5+ logins falhos em 15 min
[ ] Logs em sistema imutável (WORM / S3 Object Lock)
[ ] Time-to-detect ≤ 24h

--- SSRF (A10) ---
[ ] Metadados cloud (169.254.169.254) inacessíveis
[ ] IPs privados (10.x, 172.16-31.x, 192.168.x) bloqueados
[ ] file://, dict://, gopher:// bloqueados
[ ] URLs de webhook validadas e filtradas

--- Session Security (Web) ---
[ ] Cookies com HttpOnly, Secure, SameSite=Lax/Strict
[ ] Session timeout inativo ≤ 15 min
[ ] Session fixation prevenida (token muda após login)
[ ] Logout invalida sessão no servidor
[ ] Tokens NÃO em localStorage/sessionStorage

--- CSRF Protection ---
[ ] SameSite=Strict/Lax configurado em cookies
[ ] Token CSRF em formulários (ou header customizado)
[ ] Mutations via AJAX exigem validação CSRF
[ ] GET requests não causam efeitos colaterais

--- CSP (Content Security Policy) ---
[ ] CSP header presente com default-src 'none'
[ ] script-src sem 'unsafe-inline' e sem 'unsafe-eval'
[ ] frame-ancestors 'none' configurado
[ ] base-uri 'self' e form-action 'self' configurados
[ ] report-uri / report-to ativo

--- API Security ---
[ ] Content-Type validado no servidor (application/json)
[ ] Body size limitado (≤ 1MB JSON)
[ ] GraphQL introspection desabilitada em produção
[ ] WebSocket autenticado e com rate limiting
[ ] Paginação implementada (não retornar todos os registros)

--- Frontend Security ---
[ ] eval(), new Function(), dangerouslySetInnerHTML não utilizados
[ ] Source Maps desabilitados em produção
[ ] Third-party scripts com SRI
[ ] Dados sensíveis não no HTML source
[ ] console.log removido em produção

--- Infrastructure ---
[ ] TLS 1.2+ com cipher suites seguros
[ ] HSTS ≥ 31536000s com includeSubDomains + preload
[ ] DNS CAA configurado
[ ] SPF + DKIM + DMARC para emails
[ ] Nota mínima A em ssllabs.com/ssltest e securityheaders.com

--- Clickjacking / Tabnapping ---
[ ] X-Frame-Options: DENY presente
[ ] CSP frame-ancestors 'none' configurado
[ ] Links target="_blank" com rel="noopener noreferrer"

--- Email / Webhook Security ---
[ ] Tokens em emails são de uso único e expiram ≤ 1 hora
[ ] Webhooks com assinatura HMAC validada
[ ] Webhooks entregues apenas via HTTPS

--- Advanced Web Vulnerabilities (W11) ---
[ ] Race conditions testadas (cupons, transferências, estoque)
[ ] JWT algorithm confusion testado (alg: none, HS256 com chave pública)
[ ] OAuth/OIDC: redirect_uri whitelist, PKCE obrigatório, state validado
[ ] Prototype pollution testado (__proto__, constructor)
[ ] HTTP request smuggling testado (CL.TE, TE.CL)
[ ] Subdomain takeover verificado (CNAME dangling)
[ ] DNS rebinding testado
[ ] postMessage: event.origin validado em todos os listeners
[ ] Business logic abuse testado (preço negativo, estoque zero, desconto abusivo)
[ ] Secure randomness: crypto.getRandomValues() usado (não Math.random())
[ ] HTTP/2 rapid reset testado (CVE-2023-44487)
[ ] Web cache poisoning testado (X-Forwarded-Host, cache key injection)
[ ] ReDoS testado em regexes de validação
[ ] JSONP não utilizado (ou callbacks validados)
[ ] CORS preflight bypass testado
[ ] Account enumeration via timing testado
[ ] Integer overflow testado em campos numéricos
[ ] Open redirect testado em parâmetros de redirect

--- LGPD / GDPR Compliance ---
[ ] Política de privacidade acessível e atualizada
[ ] Consentimento granular, específico e revogável
[ ] Endpoint para titular acessar/excluir dados (Art. 18 LGPD)
[ ] Dados criptografados em repouso e em trânsito
[ ] Dados de menores protegidos (consentimento do responsável)
[ ] Logs pseudonimizados (sem PII em texto plano)
[ ] Transferência internacional de dados documentada (Art. 33 LGPD)
[ ] Procedure de resposta a incidentes em 72h (GDPR)

--- Secure SDLC / DevSecOps ---
[ ] Threat model documentado (STRIDE)
[ ] Code review com checklist de segurança
[ ] SAST no CI pipeline (Semgrep, SonarQube)
[ ] DAST em staging antes de cada deploy
[ ] Scan de secrets no CI (gitleaks, truffleHog)
[ ] Dependências monitoradas continuamente (Snyk, Dependabot)
[ ] Branch protection com PR reviews obrigatórios
[ ] Deploy exige aprovação manual
